# Ingram Cost estimate agent: deployment

Job: **turn a free-text description of AWS infrastructure into a saved, shareable AWS Pricing Calculator estimate
(calculator.aws link + per-service configuration), with a checklist so no requested service is missed.**
Same pattern as the Architecture agent (see `agent-build-playbook.md`).

```
Web UI (Amplify) -> HTTP API -> Lambda ingram-cost-api      (open, per-IP + daily cost guards)
                                  -> Lambda ingram-cost-worker (async, 15 min, no retries)
                                       -> AgentCore Runtime ingram_cost_agent (container, arm64, PUBLIC network)
                                            -> Amazon Bedrock (Claude, global.anthropic.claude-sonnet-5-5)
                                            -> AWS Pricing Calculator MCP server (Node, stdio, in the container)
                                                 -> calculator.aws (saves the estimate, returns the link)
                                  -> DynamoDB ingram-cost-runs   runs, results, activity log, cost-guard counters
```

## How a run works

1. `POST /runs` with `{"requirements": "...", "title"?}` (30 to 20,000 characters). The API writes the run to
   DynamoDB and starts the worker asynchronously; the UI polls `GET /runs/{id}` every 5 s.
2. The worker claims the run (`queued -> running`, conditional, so a duplicate delivery does nothing) and calls the
   runtime once with `{"action": "estimate", "requirements": ...}` (session `cost-run-<id>`).
3. The agent (unchanged behaviour from the original `agent/tools/`): extracts a checklist of the requested services,
   runs a Strands agent with the calculator MCP tools, blocks `build_estimate` until every requested service is in
   it (up to 2 rejections), retries the whole attempt up to 3 times, reads the saved estimate back with
   `import_estimate` and checks coverage again (log only), then checks the JSON structure.
4. The worker stores the summary on the run (status, calculator link, estimate name, service count, time), the full
   estimate JSON + checklist + coverage on `RUN#<id>/RESULT` (trimmed with a note above ~350 KB), and log lines.
   Failures end as `failed` with the stage and the error. A run still `running` after 17 minutes is marked failed.

## Access

**Open: no sign-in.** Anyone with the UI or API URL can start estimates and read every run in the shared history.
Cost guards instead of accounts: API Gateway throttling (POST /runs: 1 request/s, burst 3), `RUNS_PER_IP_HOUR`
(default 6, caller IP stored only as a SHA-256 hash) and `RUNS_PER_DAY` (default 40). Each estimate is several
Bedrock calls. Don't paste confidential details while it is open; to restrict it later, add a JWT authorizer
(Entra ID) on the HTTP API (playbook, section 6). Estimates saved on calculator.aws are reachable by anyone with
the link.

## Test and deploy

```bash
cd deployment
uv venv --python 3.12 /tmp/cost-venv && uv pip install --python /tmp/cost-venv/bin/python -r agent/requirements.txt pytest
/tmp/cost-venv/bin/python -m pytest -q agent/tests        # agent unit tests (no AWS)
/tmp/cost-venv/bin/python scripts/local_e2e.py            # API + worker + real agent server; estimate step faked
/tmp/cost-venv/bin/python scripts/local_e2e.py --bedrock  # same with real Bedrock + MCP server (credentials, node)
docker buildx build --platform linux/arm64 -t ingram-cost-agent:local --load .   # the runtime image
docker run --rm --read-only --tmpfs /tmp -p 8080:8080 ingram-cost-agent:local
python3 tools/invoke.py --local http://localhost:8080       # ping action
cp config.env.example config.env && ./scripts/deploy.sh     # image -> ECR -> sam deploy -> CORS -> config.js -> Amplify -> ping
```

`scripts/deploy.sh` needs AWS credentials, Docker with buildx, SAM CLI and Python 3 (boto3 for the smoke test).
The image tag is a hash of `Dockerfile` + `agent/`, so an unchanged agent is not rebuilt. The MCP server
(`sample-aws-pricing-calculator-mcp@1.3.3`) is installed in the image at build time; nothing is downloaded at run time.

## Layout

```
template.yaml            SAM: table, runtime + role, HTTP API, API + worker Lambdas, Amplify
Dockerfile               runtime image: Python 3.12, Node 18 + the calculator MCP server, non-root, read-only safe
agent/main.py            AgentCore entrypoint: actions estimate, ping
agent/cost_estimate/     orchestrator, mcp_tool (Strands + MCP + prompt), service_validator, validators
agent/tests/             unit tests
api/                     handler.py (routes), worker.py (runtime call, result storage), common.py (DynamoDB helpers)
ui/                      index.html, styles.css, app.js, config.js (generated by deploy.sh)
scripts/deploy.sh        full deploy;  scripts/local_e2e.py  local end-to-end test
tools/invoke.py          calls the runtime directly (SigV4) or a local container
```

## Notes

- Model: `MODEL_ID` (default `global.anthropic.claude-sonnet-5-5`, carried over from the original code and not
  verified here). A `global.` profile needs IAM on the profile, the in-Region foundation model and the Region-less
  `arn:aws:bedrock:::foundation-model/...`; the runtime role allows all three for `anthropic.*`.
- Log retention: the Lambda log groups keep 30 days; set one on the runtime log group (`LogGroup` output).
- The runs table is retained when the stack is deleted; the ECR repository is outside the stack.
